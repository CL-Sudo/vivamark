Build cache trial

With a shared cache, the pipeline's median run fell from 9.0 to 4.3 minutes over 10 runs. Two runs failed because the cache key ignored the lockfile; a one-line key fix should stop that.

Made-up example for vivamark guide report. Project: example-app. Trial: 10 runs of the main pipeline with a shared bucket cache, compared with the 10 runs before it.

At a glance

What worked

  • Median run 4.3 min, down from 9.0.
  • 6 of 10 runs restored a good cache and finished in 3.8 to 4.4 min.
  • No test changed its result because of the cache.

What did not

  • 2 runs failed on a stale cache (run-04, run-09).
  • 2 cold runs were slower than no cache: 11.2 and 10.6 min.
  • Offline runs were not tested.

Author's summary of Findings and Not done.

How the pipeline runs

  1. Checkout. Unchanged by the cache.
  2. Restore cache. 3 s on a miss, up to 41 s on a full hit.
  3. Install dependencies. 12 s on a hit, 3.1 min on a miss.
  4. Build. Gains least on a stale hit: a failed build still runs most of the way.
  5. Test. Unchanged by the cache.
  6. Save cache. Runs on every passed run; 35 s after a cold run.

Findings

  1. The cache halves a typical run. Median 4.3 min over the 10 trial runs, against 9.0 min over the 10 runs before it. On a good hit, installing dependencies drops from 3.1 min to 12 s and the build from 5.2 min to about 1 min. Sure: the same pipeline and runner type throughout.
  2. A stale cache broke two runs. The cache key was the branch name only, so after a dependency update run-04 and run-09 restored the old packages and the build failed. Evidence: both logs show the old version installed (logs/run-04.txt, line 212). Sure: reproduced once by hand.
  3. A cold run costs more than no cache. run-01 and run-07 took 11.2 and 10.6 min: a full install and build, plus about 35 s to save the cache and a few seconds on the failed restore. Fairly sure: two runs only.
  4. Checkout and test do not change. Their times stay within a few seconds whether the cache hits or not, so the gain is all in install and build.

Author's summary of the options table. Each cell is the author's reading of that table: partly means for some steps only, or only with extra setup; n/d means not tested in this trial.

OptionWhat it does and costs
Runner diskKeeps the cache on the runner's own disk. Fast to restore, but lost whenever a fresh runner starts, which is most runs on hosted runners. Caches dependencies fully and build outputs only for unchanged modules. Needs nothing else.
Shared bucketUploads the cache to a storage bucket after each passed run. Survives fresh runners; needs network access and a bucket with a lifecycle rule. Same coverage of dependencies and build outputs as runner disk. This is what the trial used.
Remote build cacheA build tool's own remote cache, shared per build target. Caches build outputs well and dependencies only through the build tool. Needs a service to run and secure. Offline behaviour was not tested.
No cache (today)Today's setup. Every run installs and builds from scratch: median 9.0 min over the 10 runs before the trial.

Not done or not checked

  • Runs without network access: the bucket needs it, and no offline runner was available.
  • The remote build cache was compared on paper only, from its documentation.
  • Only the main pipeline; feature branches still run without a cache.

Ideas, by cost

Cheap

  1. Add the lockfile hash to the cache key. Would have prevented both failures.
  2. Skip saving when the restore was an exact hit: about 20 s a run.

Medium

  1. Cache dependencies and build outputs separately, so one going stale does not cost the other.
  2. Warm the cache with a nightly run on main, so the first run of the day is not cold.

Costly

  1. Run a remote build cache: the most build time saved, and a service to keep.
